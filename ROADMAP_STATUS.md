## Design Note — Scheduled outbox_seq allocation (Pre-step findings 2026-08-30)

**Findings from `services/api/main.go:179` (prepare) and `services/api/main.go:259` (send):**
- `prepare` is the ONLY allocation path for `outbox_seq` via `outbound_message_seq` sequence (`INSERT outbound_reservations ... DEFAULT nextval('outbound_message_seq')` returning `reservation_id, outbox_seq, encryption_version=1, aad_version=1, expires_at now()+10m`). Validates `X-User-Id + mailbox ownership + is_active`, rate 60/min + 1MB.
- `send` validates canonical envelope (`0x01||nonce12||ct`, `iv==nonce`), HPKE (`0x01||enc32||ct`), versions==1, then `SELECT outbound_reservations FOR UPDATE`, checks `reserved` not `consumed/expired`, matches `mailbox_id/user_id/outbox_seq/encVer/aadVer`, looks up `domain_id`, generates `delivery_id`, `INSERT outbound_queue` with immutable AAD fields + `reservation_id` + `expires_at now()+7d` + idempotent `ON UNIQUE(reservation_id)` + `UPDATE reservations consumed`.

**Confirmed design for Scheduled:** No new allocation path, no expiry extension. `POST /v1/outbound/schedule` reuses `prepare` allocation: client calls `prepare` → gets `outbox_seq` → encrypts with `canonical_aad(mailbox_id,outbox_seq,1,1)` → calls `schedule` with `reservation_id + scheduled_at`. Handler `FOR UPDATE` validates same reservation checks as `send`, computes `send_token_hash=SHA256(wrapped)`, `INSERT scheduled_messages` with same AAD columns + `scheduled_at` + `expires_at now()+7d` + `status pending`, then `UPDATE reservations consumed` (so 10m expiry never extends; consumed row is inert even if `scheduled_at` is +30d). Scheduler `poll_scheduled` copies verbatim to `outbound_queue` without decryption or re-allocation, idempotent via `ON CONFLICT(reservation_id)`.

Rejected alternative (allocate inside schedule via `nextval` without prepare) would break AAD binding because client needs `outbox_seq` at encrypt time.
