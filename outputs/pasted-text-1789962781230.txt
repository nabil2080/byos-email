## 1. WHAT BYOS IS

BYOS is a business-email service where:

- Customers provide their own persistent storage (S3, Google Drive, 
  S3-compatible providers). BYOS never stores mailbox content on its 
  own servers.
- Internal BYOS-to-BYOS mail is end-to-end encrypted with post-quantum 
  hybrid cryptography (X-Wing = X25519 + ML-KEM-768).
- External mail (to Gmail, Outlook, etc.) uses traditional SMTP with 
  a transient plaintext window, relayed through Amazon SES.
- The product is priced by graduated per-seat brackets with a 10-seat 
  minimum. No named plans. No feature gating.

The pitch: "As private as Proton or Tuta, plus customer-controlled storage."

## 4. TWO CRYPTOGRAPHIC FORMATS (IMPORTANT)

BYOS uses two distinct formats for two distinct purposes. Do NOT 
confuse them.

### Format 1 — Storage encryption (binary)

- Purpose: at-rest encryption of inbound external mail (mail already 
  received in plaintext by the inbound pipeline)
- Format: `version(1 byte) || nonce(12 bytes) || ciphertext+tag(N bytes)`
- Wrapped content key: stored in Postgres in 
  `message_metadata.content_key_hpke_wrapped`
- Object location: MinIO/S3 at `mailboxes/<mailbox_id>/<seq>.eml.enc`
- Algorithm TODAY: X25519-only classical HPKE
- Algorithm GOAL: X-Wing hybrid (this is the pending task — see §7)

### Format 2 — End-to-end envelope (JSON)

- Purpose: internal BYOS-to-BYOS mail where the outbound worker routes 
  without decrypting
- Format: canonical JSON with fields `v, alg, key_id, key_epoch, enc, 
  nonce, ciphertext, sig`
- Wrapped content key: embedded in the envelope's `enc` field
- Algorithm: X-Wing hybrid KEM (X25519 + ML-KEM-768) via HPKE + AES-256-GCM
- Used by: client (Rust/WASM) for internal mail composition
- Status: spec complete, not yet wired into the pipeline

## 5. WHAT HAS BEEN BUILT AND VERIFIED

### Crypto core — COMPLETE AND VERIFIED

Two independent implementations exist and pass byte-for-byte parity:

- **Go crypto** at `crypto/` — verified against X-Wing draft-10 
  Appendix C (3 vectors) and RFC 9180 Appendix A.1.1 (KEM + key 
  schedule). All tests pass.
- **Rust/WASM crypto** at `crypto-core/` — verified byte-for-byte 
  identical to Go across 14 cross-language test vectors. Compiles 
  to `wasm32-unknown-unknown`. Release WASM is ~545 KB.

Both implementations support:
- X-Wing hybrid KEM (correct combiner per draft-10, label `\.//^\`)
- HPKE key schedule per RFC 9180
- Ed25519 signing key primitive (used in recovery ceremonies, not 
  yet wired into E2E mail)
- Envelope canonical JSON serialization
- AAD construction binding all metadata

**Do not modify the crypto core without understanding the test 
vectors.** Every change must still pass the external vectors.

## 7. CURRENT GAP — NEXT PRIORITY

**Storage path uses X25519-only, not X-Wing.**

This is the pending task. The crypto core supports X-Wing (verified), 
but the storage pipeline still uses the classical X25519 path. This 
means inbound external mail — the majority of a typical mailbox — is 
NOT post-quantum safe at rest.

Fixing this requires:
1. Adding `encrypt_message_xwing` and `decrypt_message_xwing` to 
   crypto-core
2. Schema migration to widen `content_key_hpke_wrapped` (X-Wing wrapped 
   keys are ~1170 bytes vs ~81 for X25519)
3. Adding a `wrapped_key_algorithm` column to message_metadata
4. Wiring native-crypto-worker to use X-Wing when available
5. Adding `mailbox_xwing_pk` column to mailboxes
6. Verifying end-to-end: send test email → stored blob uses X-Wing → 
   decrypts correctly

Estimated work: 2–4 days.

## 9. WORKING PRINCIPLES

These are non-negotiable. Every task must respect them.

1. **Spec before code.** For any crypto or architecture change, update 
   the spec or roadmap first. Do not implement crypto without a 
   spec that has been reviewed.

2. **External verification.** Every crypto primitive must be validated 
   against an external reference (IETF draft, RFC test vector, NIST 
   known-answer test). Self-referential tests prove nothing.

3. **Byte-exact cross-language parity.** When Go and Rust both 
   implement the same algorithm, they must produce byte-identical 
   output for the same inputs. Cross-language test vectors enforce this.

4. **Don't break working code.** If a pipeline works, don't rewrite it 
   without a specific reason. The X25519 path stays even after X-Wing 
   is added, for backward compatibility.

5. **No plaintext persistence.** The server must not write plaintext 
   mailbox content to disk, database, or object storage — ever.

6. **Honest claims.** The roadmap and docs must not overstate what 
   BYOS protects. Section P exists to keep claims calibrated.
