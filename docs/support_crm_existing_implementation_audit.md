## 1. Executive Summary

### Verdict: Mostly Mock / Demo with Limited Backend Organization Management

The existing Support CRM in the BYOS repository is **predominantly a frontend demo with simulated telemetry and hardcoded mock ticketing**. While it contains genuine backend connectivity for B2B organization lifecycle management, seat billing updates, and append-only audit logging, **the core ticketing and customer support functionality does not exist in any functional capacity**.

Furthermore, **the Customer-Facing Help Desk is completely absent across all customer applications** (`apps/webmail`, `apps/control-plane`, and `apps/public-site`).

### Key Evidence Supporting This Verdict:

1. **Ticketing Backend Is Pure Mock:**
   - In `services/admin-api/main.go` (`ticketsHandler`, lines 97–131), the `/admin/v1/tickets` endpoint returns a hardcoded in-memory JSON array of three mock tickets (`tkt_9a10f82`, `tkt_1b83d90`, `tkt_3c44e12`).
   - There are **zero database tables** for tickets, ticket messages, replies, attachments, internal notes, or assignments in PostgreSQL.
   - The Support CRM frontend (`apps/support-crm/src/App.tsx`, line 235) does not even fetch `/admin/v1/tickets`; it initializes tickets with an in-memory client-side constant `MOCK_TICKETS`.
2. **Customer Help Desk Does Not Exist:**
   - Search across `apps/webmail`, `apps/control-plane`, and `apps/public-site` shows **zero ticket creation forms**, **zero customer ticket portals**, and **zero help desk article models**.
   - `apps/public-site/src/pages/docs.astro` contains only 6 hardcoded static cards linking out to Control Panel settings or `/security`.
3. **Decryption Is a Frontend Illusion:**
   - In `apps/support-crm/src/App.tsx` (`handleDecryptTicket`, lines 554–575), clicking "Decrypt with YubiKey" calls `navigator.credentials.get()` with a dummy random challenge. When the browser WebAuthn prompt succeeds, it merely displays an alert banner ("*Hardware Key Assertion verified. Ticket payload decrypted into secure memory enclave*"). No cryptographic decryption occurs, and no decrypted message payload is displayed.
4. **Telemetry Stream Is a Timer Simulation:**
   - In `apps/support-crm/src/App.tsx` (lines 246–272), the live telemetry feed is generated by a client-side `setInterval(..., 4500)` selecting random strings from a local `SIMULATED_POOL` array.
5. **Real Functionality Exists Only for Org Management:**
   - Real PostgreSQL interactions exist in `services/admin-api/handlers/organizations.go` and `pricing.go` for listing organizations, updating subscription status, adjusting seat capacities, and recording audit records to `support_audit_logs`.

### 4.2 Database Role `role_support_agent`

The dedicated PostgreSQL role `role_support_agent` enforces column-level security:
- **`organizations`**: `SELECT (id, name, default_storage_connection_id, created_at, updated_at, plan, status)`, `UPDATE (plan, status, updated_at)`.
- **`users`**: `SELECT (id, org_id, email, display_name, is_active, created_at, updated_at, two_factor_enabled)`. `password_hash`, `recovery_auth_pk`, and `totp_secret_enc` are **DENIED**.
- **`mailboxes`**: `SELECT (id, org_id, user_id, domain_id, local_part, mode, root_secret_id, mailbox_pk, is_active, created_at, updated_at)`. `mailbox_sk_wrapped` is **DENIED**.
- **`domains`**: `SELECT (id, org_id, name, is_verified, dkim_selector, dkim_public_key, created_at)`. `dkim_private_key_enc` is **DENIED**.
- **`storage_connections`**: `SELECT` permitted except `credentials_enc` which is **DENIED**.
- **`support_audit_logs`**: `SELECT`, `INSERT`.

## 6. Authentication and Permission Model

### 6.1 Staff Authentication (`services/admin-api`)
- **Current State**: Staff authentication is completely mocked via `mockWebAuthnMiddleware` in `services/admin-api/main.go`.
- If `BYOS_DEV_MODE != "1"`, the middleware rejects all requests with HTTP 401 ("*mock WebAuthn disabled in production*").
- There is no real WebAuthn challenge verification, session store, or staff user management implemented in Go.
- Token validation is a static string match: `Authorization == "Bearer mock-support-agent"`.

### 6.2 Customer Authorization Boundary
- While `services/api` enforces strict cookie-based session authentication for mailbox users and organization admins, **it provides no endpoints or authorization models for support tickets**.
- Consequently, multi-tenant isolation for ticket access (ensuring Customer A cannot view Customer B's tickets) is currently unbuilt.

### 6.3 Zero-Knowledge Database Privilege Boundary
- As verified via non-mutating PostgreSQL inspection, the `role_support_agent` database role has strict column-level restrictions preventing SELECT of cryptographic keys:
  - Attempting to query `password_hash` on `users` raises `ERROR: permission denied for table users`.
  - Attempting to query `mailbox_sk_wrapped` on `mailboxes` raises `ERROR: permission denied for table mailboxes`.
- This represents a solid, compliant security foundation for the future Support CRM backend.

## 7. Email and Notification Integration

### 7.1 Existing Email Delivery Subsystems
1. **Outbound User Mail**: Relayed via `services/outbound-worker` (Rust/Lettre) through local Postfix MTA with DKIM signing.
2. **Inbound Mail**: Received on port 25 via `services/inbound-bridge` (Go/`go-smtp`), analyzed by Rspamd, encrypted by `services/mail-router`, and stored in object storage.
3. **System Security Emails**: `services/api/otp_delivery.go` transmits transactional emails (password reset, 2FA OTP) directly via SMTP using Go `net/smtp`.

### 7.2 Support Email Audit
- **Ticket Confirmation Emails**: **Missing**. No transactional template or send trigger exists.
- **Agent Reply Notification Emails**: **Missing**.
- **Customer Email Reply Ingestion**: **Missing**. Inbound bridge has no handler to parse incoming messages to `support@<domain>` or extract threading tokens (e.g., `ticket+TKT-12345@support.byos.local`).
- **Reserved Alias Block**: `services/api/aliases.go` explicitly marks `support` as a reserved keyword, preventing mailboxes from claiming `support@<domain>`.

## 8. Security and Privacy Findings

### 8.1 Strengths & Strong Invariants
1. **Database Role Privileges**: `role_support_agent` cannot read user passwords, private keys, or recovery verifiers.
2. **Immutable Audit Ledger**: `support_audit_logs` uses an unbypassable trigger that aborts any `UPDATE` or `DELETE` statement.
3. **No WASM in CRM**: `apps/support-crm` does not import `byos_crypto_core`, ensuring support staff cannot decrypt customer mailbox envelopes in the browser.

### 8.2 Demonstrated Deficiencies & Security Risks
1. **Authentication Bypass in Dev Mode**: `services/admin-api` accepts static token `Bearer mock-support-agent` when `BYOS_DEV_MODE=1`.
2. **Fake YubiKey Decryption**: `handleDecryptTicket` simulates decryption with browser WebAuthn credentials without performing real asymmetric decryption or verifying public keys against a hardware token.
3. **Vite Proxy Port Discrepancy**: `apps/support-crm/vite.config.ts` proxies `/admin/v1` to port `8087`, while `services/admin-api/main.go` falls back to `8090` if `PORT` is unset (resolved in Docker via `PORT: "8087"`).
4. **Lack of Rate Limiting on Admin API**: `services/admin-api` lacks request throttling and IP rate limiting.

## 10. Prioritized Missing Functionality Backlog

### P0: Critical Security & Architectural Foundations
1. **Ticketing Database Schema**: Create tables in PostgreSQL for `support_tickets`, `support_ticket_messages`, `support_ticket_attachments`, and `support_agents`.
2. **Staff Identity & Session Model**: Implement authenticated staff sessions for `admin-api` (FIDO2/WebAuthn or cryptographically verified staff tokens, replacing the mock token).
3. **Customer Authorization Middleware**: Implement ticket ownership checks in `services/api` so users can only access tickets belonging to their user ID or organization.
4. **Zero-Knowledge Security Boundary**: Support tickets must operate strictly on operational metadata and user-submitted text; they must never access mailbox private keys or message envelopes.

### P1: Core Functional MVP (Help Desk + Support CRM)
1. **Customer Ticket Submission**: In-app modal/page in Webmail and Control Plane (subject, issue category, priority, description, attachment upload).
2. **Customer Ticket Portal**: View ticket list, ticket status (Open, In Progress, Resolved), conversation history, and customer reply box.
3. **CRM Ticket Queue**: Real ticket queue in `apps/support-crm` backed by PostgreSQL (sorting by priority, date, status).
4. **CRM Conversation View & Reply**: Support agent view of ticket thread with ability to send public replies and change ticket status.
5. **Private Internal Notes**: Agent-only internal notes within ticket threads (`is_internal_note = true`) hidden from customer API responses.
6. **Agent Assignment**: Ability to assign tickets to specific support agents or queues.

### P2: Communication & Knowledge Infrastructure
1. **Email Notification Pipeline**: Outbound email notification to customer upon ticket creation and agent reply using `otp_delivery` or dedicated SMTP client.
2. **Inbound Reply Ingestion**: Parse incoming emails to `ticket+<uuid>@support.byos.local` via `inbound-bridge` and append to the ticket conversation.
3. **Help Center / Knowledge Base**: Searchable articles and category browser in public site and control plane.
4. **Diagnostic Log Attachment**: Client-side sanitized diagnostic dump (WASM error codes, storage probe status) attachable to support tickets.

### P3: Advanced Governance & Analytics
1. **SLA Tracking & Warning Badges**: Time-to-first-response and resolution metrics.
2. **Real Telemetry Aggregator**: Replace simulated ticker in Support CRM with genuine Prometheus / Redis queue depth telemetry.
3. **Canned Responses / Macros**: Saved snippet templates for support agents.

## 11. Recommended Implementation Architecture

### 11.1 Shared Ticketing Backend with Dual Interfaces
Rather than creating separate backend services or adopting heavy third-party platforms, BYOS should implement a **unified ticketing core in the existing Go backend services**:

1. **Customer-Facing API (`services/api`)**:
   - Handles customer ticket submission, conversation retrieval, customer replies, and Help Center article search.
   - Enforces customer authentication and organization tenancy.
2. **Internal Admin API (`services/admin-api`)**:
   - Handles ticket queue management, agent replies, internal notes, assignments, and ticket status changes.
   - Enforces staff authentication and writes all operator actions to `support_audit_logs`.
3. **Shared PostgreSQL Database (`byos`)**:
   - Stores ticket entities, messages, attachments, and categories.
   - Leverages `role_support_agent` with granted permissions on support tables while maintaining strict `DENY` on user encryption keys.
