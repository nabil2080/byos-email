# BYOS V5.3 Final Architecture Spec

**Status:** FROZEN — no further architecture revision unless a real test uncovers a flaw.
**Date:** 2026-08-28

## 1. Key Hierarchy

```
mnemonic (BIP39 24-word)
  → HKDF-SHA256(salt="byos-mnemonic-v1", ikm=entropy, info="byos-root-v1")
    → root_secret (32 bytes)
      → mailbox_sk = AES-GCM-wrap(root_secret, mailbox_sk_bytes, AAD=mailbox_id||"mailbox-sk-v1")
        → content_key (random 32 bytes per message)
          → AES-GCM-encrypt(content_key, plaintext, canonical_aad)
```

- **root_secret** is per-mailbox (one root per mailbox, not per org).
- **content_key** is random per-message, never reused.

## 2. Canonical AAD (29 bytes, fixed)

```
mailbox_id(16) || message_seq(8, big-endian) || encryption_version(4, big-endian) || aad_version(1)
```

- `mailbox_sk_version` is NEVER in AAD.
- Each encryption uses a fresh 96-bit CSPRNG nonce.
- Nonces MUST NOT repeat with the same content_key.

## 3. Canonical AES-GCM Envelope

```
version(1 byte) || nonce(12 bytes) || ciphertext_with_tag(variable)
```

- Version: `0x01`
- Nonce: fresh 96-bit CSPRNG per encryption.

## 4. Canonical HPKE Wire Format

```
version(1) || enc(32) || ciphertext(N)
```

- Single `hpke_wrapped bytea` column everywhere.
- Suite: DHKEM(X25519, HKDF-SHA256) + AES-256-GCM (RFC 9180).

## 5. Canonical Bundle Hash Serialization

```
version(1) || storage_object_id_len(4) || storage_object_id || ciphertext_len(8) || ciphertext ||
content_key_wrapped_len(4) || content_key_wrapped || encryption_version(4) || mailbox_sk_version(4) ||
encryption_iv(12) || aad_version(1)
```

→ SHA-256.

## 6. Root Secrets (no circular FK)

- `root_secrets` table has NO `mailbox_id` column.
- `mailboxes.root_secret_id` is `NOT NULL` from creation.
- `root_secrets.version` tracks recovery-root lineage (new row per rotation).
- `mailboxes.mailbox_sk_version` tracks mailbox-key lineage (mutable field).
- `message_metadata.encryption_version` is immutable, part of AAD.

## 7. Three Independent Version Concepts

| Field | Table | Mutability | Role |
|-------|-------|------------|------|
| `root_secrets.version` | root_secrets | New row per rotation | Recovery-root lineage |
| `mailboxes.mailbox_sk_version` | mailboxes | Mutable field | Mailbox-key lineage |
| `message_metadata.encryption_version` | message_metadata | Immutable | Encryption scheme (in AAD) |

## 8. Org Recovery Model

- Admin browser generates `org_recovery_sk` / `org_recovery_pk`.
- Server stores wrapped material only.
- Recovery: admin enters passphrase locally → Argon2id → `passphrase_key` → AES-GCM decrypt `org_recovery_sk` → HPKE-Open `root_secret` → AES-GCM decrypt `mailbox_sk`.
- Server NEVER possesses unwrapped customer cryptographic private keys.
- Org recovery key is **IMMUTABLE in V1**. No `passphrase_hash` in `org_recovery_principals`.

## 9. Mailbox Privacy Modes

| Mode | root_secret_wrapped | Recovery Path |
|------|---------------------|---------------|
| Private | `NULL` | Mnemonic only |
| Org-managed | `HPKE-Seal(root_secret, org_recovery_pk)` | Admin recovery principal |

- Private mailbox: NO org recovery path. Root rotation: new mnemonic shown to owner.
- Org-managed: Employee NEVER receives mnemonic (not even during root rotation).

## 10. Delivery Identity

- `UNIQUE(mailbox_id, delivery_identity)`
- With Message-ID: `SHA-256(normalized(Message-ID) || normalized(sender) || normalized(sorted_recipients))`
- Without Message-ID: `SHA-256(normalized(sender) || normalized(sorted_recipients) || canonical_envelope || canonical_RFC5322_message_bytes)`

## 12. Inbound Pipeline

Dedicated SMTP ingress proxy (NOT Postfix before-queue filter).
- Encrypt before durable storage.
- Failure → 4xx, sender retries.
- No plaintext queue. No LUKS exception for inbound.
- Inbound content keys: **Server generates**.

## 13. Outbound Pipeline

**Overview:** Client generates `send_token = content_key` (32B CSPRNG). Client AES-256-GCM-encrypts message with `send_token` and canonical outbound AAD, HPKE-Seals `send_token` to `outbound_delivery_pk`. API queues `encrypted_message` + `send_token_hpke_wrapped` (+ immutable AAD metadata). Dedicated `outbound-worker` (only holder of `outbound_delivery_sk`) HPKE-Opens, decrypts transiently, DKIM-signs, submits to Postfix.

- Outbound content keys: **Client generates**.
- Single outbound key is V1 operational trust boundary.

**V1 exception:** Postfix queue may contain transient plaintext. Protected by encrypted filesystem, restricted permissions, no backups, short retention.

### 13.1 Outbound Reservation Model

`POST /v1/outbound/prepare` is the ONLY way to obtain a server-assigned `outbox_seq`. It is **authenticated** and **authorized**:

* Requires valid session; verifies `mailbox_id` belongs to `user_id`, `is_active=true`, and sending is allowed under rate limits/policy.
* Creates explicit reservation row:

```
outbound_reservations (
  reservation_id uuid PK,
  user_id uuid NOT NULL,
  mailbox_id uuid NOT NULL,
  outbox_seq BIGINT NOT NULL, -- from outbound_message_seq sequence
  encryption_version INTEGER NOT NULL DEFAULT 1,
  aad_version SMALLINT NOT NULL DEFAULT 1,
  status TEXT CHECK (reserved|consumed|expired) DEFAULT 'reserved',
  created_at timestamptz DEFAULT now(),
  expires_at timestamptz NOT NULL DEFAULT now()+ interval '10 minutes'
  UNIQUE(mailbox_id, outbox_seq)
)
```

* Returns `{reservation_id, outbox_seq, encryption_version, aad_version}`.
* Reservation is **single-use**, **bound to user_id+mailbox_id**, **expires in 10 minutes** if not consumed. Gaps from expired reservations are acceptable.

### 13.2 Authenticated Consumption (Atomic)

`POST /v1/outbound/send` must be atomic:

```sql
BEGIN;
SELECT * FROM outbound_reservations
 WHERE reservation_id=$1 AND mailbox_id=$2 AND user_id=$3
   AND status='reserved' AND expires_at>now() FOR UPDATE;
-- API validates structural fields only: mailbox_id, outbox_seq, encryption_version, aad_version match reservation;
-- envelope structure valid (1||nonce12||ct+tag) and encryption_iv == envelope[1..13]; HPKE wrapper is 1||enc32||ct.
-- API MUST NOT claim it cryptographically verifies AAD was used during encryption.
-- Actual cryptographic verification happens in outbound-worker:
--   canonical_aad(mailbox_id, outbox_seq, encryption_version, aad_version)
--     → HPKE-Open(send_token_wrapped, outbound_delivery_sk, AAD)
--     → AES-GCM-Decrypt(envelope, send_token, AAD)
-- Only that path proves AAD binding.
INSERT INTO outbound_queue (delivery_id, mailbox_id, domain_id, recipient, encrypted_message, send_token_hpke_wrapped, outbox_seq, encryption_version, aad_version, encryption_iv, reservation_id, status, expires_at) VALUES (...);
UPDATE outbound_reservations SET status='consumed' WHERE reservation_id=$1;
COMMIT;
-- Idempotent retry: if status='consumed' already, SELECT delivery_id FROM outbound_queue WHERE reservation_id=$1 and return existing delivery_id (no second row). See 13.9.
```

Rejects: expired, already consumed (→ idempotent return), wrong seq/version, unauthorized user/mailbox, malformed envelope/iv mismatch.

### 13.3 Exact Outbound AAD & Envelope

*Outbound canonical AAD* (29B, shared by Rust crypto-core, WASM, outbound-worker, tests — **no separate TypeScript AAD implementation**):

```
mailbox_id(16) || outbox_seq(8 BE) || encryption_version(4 BE) || aad_version(1)
```

`mailbox_sk_version` is **never** in AAD.

*Canonical AES-GCM envelope* (authoritative nonce source):

```
version(1=0x01) || nonce(12) || ciphertext+tag(variable)
```

`encryption_iv` column is **redundant metadata** — API parses envelope, extracts `envelope[1..13]`, verifies `encryption_iv == nonce`. Stored only if schema requires; decryption uses **envelope nonce**, never the separate column alone. Mismatch → reject.

*Canonical HPKE wire format:* `0x01 || enc(32) || ct(N)` (X25519/HKDF-SHA256/AES-256-GCM, RFC 9180).

### 13.4 Send Token

```
send_token == content_key (32B CSPRNG)
client: AES-GCM(send_token, plaintext, outbound AAD) → envelope
        HPKE-Seal(send_token, outbound_delivery_pk, outbound AAD) → wrapped
server: HPKE-Open(wrapped, outbound_delivery_sk, outbound AAD) → send_token
        AES-GCM-Decrypt(send_token, envelope, outbound AAD) → plaintext (transient)
```

Server **never** receives unwrapped `send_token` separately.

### 13.5 Outbound Worker Boundary (Option A)

* `outbound_delivery_sk` lives **only** inside `outbound-worker` via Docker secret `/run/secrets/outbound_delivery_sk` (`OUTBOUND_DELIVERY_SK_B64` never in image, git, `.env.example`, API, crypto-worker, mail-router, PostgreSQL, Redis, MinIO, host FS, frontend/WASM). `outbound-worker` is Rust binary linking `byos-crypto-core` natively.
* `outbound-worker` must NOT receive `mailbox_sk`, `root_secret`, `mnemonic`, or inbound `content_key` wrappers.
* `outbound-worker` only decrypts rows from `outbound_queue`/`scheduled_messages`; plaintext exists only transiently for DKIM + `smtp.Dial(postfix:587)` submission.
* `crypto-worker` does **not** hold `outbound_delivery_sk` and exposes **no** outbound decrypt endpoint.
* `mail-router` does **not** hold `outbound_delivery_sk`.

### 13.6 Public Key Source of Truth

`GET /v1/outbound/pubkey → {outbound_delivery_pk: base64}` is canonical runtime source; API holds only public key. No `OUTBOUND_DELIVERY_SK` in API. Optional `NEXT_PUBLIC_OUTBOUND_DELIVERY_PK` build-time cache must be documented as cache and verified against runtime `GET` at startup.

### 13.7 Scheduled Send

Uses same `outbound_reservations` + `scheduled_messages` + `outbound_queue` capability model (send_token HPKE-wrapped to same `outbound_delivery_pk`); scheduler moves `scheduled_messages` → `outbound_queue` at `scheduled_at` without ever holding plaintext.

### 13.8 SMTP Hop (outbound-worker → Postfix)

`outbound-worker → Postfix` uses **internal `postfix:25` with trusted internal-network access** (`mynetworks` includes `172.18.0.0/16`, `permit_mynetworks`). No SASL auth required inside Docker network. External clients use `submission 587` with SASL. Plaintext exists transiently only in Postfix outbound spool — the documented V1 exception (encrypted filesystem, restricted permissions, no backups, short retention). No separate 587 auth is used by the worker.

### 13.9 Idempotent Retry (Network Ambiguity)

`POST /v1/outbound/send` is idempotent per `reservation_id`:
* `FOR UPDATE` lock on `outbound_reservations`.
* If `status='consumed'` → `SELECT delivery_id FROM outbound_queue WHERE reservation_id=$1` → return existing `delivery_id` (no second row).
* `UNIQUE(reservation_id)` on `outbound_queue` enforces exactly one delivery per reservation; duplicate `INSERT` returns existing `delivery_id`.
* `expired` → `410`, not found → `404`.

### 13.10 Docker Secret for outbound_delivery_sk

`outbound_delivery_sk` (32B base64) is provisioned as Docker secret `/run/secrets/outbound_delivery_sk` mounted **only** in `outbound-worker` (`secrets:` + `secrets:` + `environment: OUTBOUND_DELIVERY_SK_FILE=/run/secrets/outbound_delivery_sk`). It never appears in `git`, `.env.example`, `Dockerfile` `ENV`, image layer, `api`, `crypto-worker`, `mail-router`, `postgres`/`redis`/`minio`, frontend/WASM, or host FS. Public key is via `GET /v1/outbound/pubkey` (reads `OUTBOUND_DELIVERY_PK_B64` or `/run/secrets/outbound_delivery_pk`).

## 14. Search

- Client-derived `search_key = HKDF(root_secret, "byos-search-key-v1")`.
- Server stores ONLY HMAC tokens in `search_index`.
- Server NEVER stores `search_key`.
- Search is client-only (Category 1).
- V1 simple token matching, no ranking/phrase search.

## 15. Bridge

- Local native binary (same Rust codebase: wasm32 for webmail, native for Bridge).
- "Bridge necessarily handles plaintext transiently on the user's computer."
- "Bridge NEVER sends plaintext to BYOS server."

## 16. Device Enrollment

- Client possesses root_secret.
- HPKE-Seals to device_pk.
- Uploads `wrapped_root_secret`.
- Server stores wrapped only.

## 17. Archive vs Delete

- **Archive:** preserves keys (recoverable).
- **Delete:** destroys all keys (unrecoverable).

## 18. Crypto Erasure

- DELETE = logical deletion.
- DEK rotation = cryptographic capability destruction.
- Backups reconciled separately.

## 19. Backup

- `BEK` (Backup Encryption Key) separate from `DEK`.
- Restore reconciliation: check `delivery_log` for stale capabilities.
- Stale Postfix spool NOT backed up.

## 20. Privacy Guarantee (Precise)

"Persistent customer mailbox storage contains encrypted content. Required SMTP components process plaintext transiently. V1 explicitly permits temporary plaintext persistence in the outbound Postfix spool, protected by encrypted storage, restricted permissions, no backups, and short retention."

## 21. Removed from V1

- Auto-forwarding (removed entirely).
- Auto-reply: Category 3 (explicit server-readable). Template stored plaintext, user consents.

## 22. Nonce Policy

- Fresh 96-bit CSPRNG per encryption.
- Each message gets fresh random 256-bit content_key.
- Nonces MUST NOT repeat with same content_key.
- No deterministic/counter-based construction.
