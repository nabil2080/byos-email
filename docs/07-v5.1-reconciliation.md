## Objective

Resolve every blocking inconsistency identified during V5.0 review. This document replaces the affected sections of V5.0. The core cryptographic hierarchy, HPKE construction, Rust/WASM boundary, and client-generated key model are unchanged.

After approval of V5.1, the cryptographic protocol is frozen and implementation begins.

## 1. Root-Rotation Mnemonic Derivation (FIX)

### V5.0 Bug

Root rotation created a mnemonic that would not reproduce the root_secret actually used:

```text
WRONG (V5.0):
  new_root_secret = CSPRNG(32)
  new_entropy = new_root_secret
  new_mnemonic = Encode(new_entropy)

Recovery later:
  new_mnemonic → Decode → new_root_secret → HKDF → ??? (different value)
```

The HKDF step during recovery produces a different value than the raw CSPRNG bytes used as root_secret during rotation.

### V5.1 Fix

Mnemonic always encodes raw entropy. root_secret is always derived via HKDF from that entropy. The derivation path is identical for initial creation and root rotation.

```text
Initial setup:
  entropy = CSPRNG(32)
  root_secret = HKDF-SHA256(salt = "byos-mnemonic-v1", ikm = entropy)
  mnemonic = BIP39-Encode(entropy)

Root rotation:
  new_entropy = CSPRNG(32)
  new_root_secret = HKDF-SHA256(salt = "byos-mnemonic-v1", ikm = new_entropy)
  new_mnemonic = BIP39-Encode(new_entropy)

Recovery from mnemonic:
  entropy = BIP39-Decode(mnemonic)
  root_secret = HKDF-SHA256(salt = "byos-mnemonic-v1", ikm = entropy)
```

The mnemonic is a representation of the entropy. The root_secret is always derived. This is true for initial setup, root rotation, and recovery. The derivation never changes.

### Implementation

```rust
fn derive_root_secret(entropy: &[u8; 32]) -> [u8; 32] {
    let hk = Hkdf::<Sha256>::new(Some(b"byos-mnemonic-v1"), entropy);
    let mut root_secret = [0u8; 32];
    hk.expand(b"", &mut root_secret).expect("HKDF expansion failed");
    root_secret
}
```

## 2. Scheduled Send (FIX)

### V5.0 Contradiction

The architecture described a plaintext `send_token` but the schema stored `send_token_hash`. A hash cannot decrypt anything.

### V5.1 Design

Scheduled Send intentionally creates a narrow, time-scoped server-side decryption capability for exactly one message. This is an explicit design choice, not a loophole.

```text
User composes message
  ↓
Client encrypts message with content_key
  ↓
Client generates send_token (32 random bytes)
  ↓
Client seals send_token with HPKE using mailbox_pk
  ↓
Client sends to server:
  - encrypted message (content_key sealed to mailbox_pk)
  - send_token_hpke_wrapped (send_token sealed to mailbox_pk)
  - scheduled_time
  ↓
Server stores:
  - encrypted message in storage
  - send_token (plaintext) in database, encrypted at rest with server key
  - scheduled_time
  ↓
At scheduled time:
  - Server retrieves send_token
  - Server unwraps the message content_key using send_token
  - Server sends the message
  - Server deletes send_token from database
  - Message is gone from server memory
```

### Why the Server Can Decrypt

The user explicitly consents: "I want the server to send this message at a future time." The send_token is a scoped, single-message, time-limited capability. The server can only use it once, only before the scheduled time, and only for that specific message.

### Database Schema

```sql
CREATE TABLE scheduled_messages (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    mailbox_id      uuid NOT NULL REFERENCES mailboxes(id),
    domain_id       uuid NOT NULL REFERENCES domains(id),
    recipient       text NOT NULL,
    subject         text,
    body_text       text,

    -- The message is encrypted. content_key is unwrapped using send_token.
    encrypted_message   bytea NOT NULL,
    hpke_wrapped_key    bytea NOT NULL,   -- content_key HPKE-wrapped to mailbox_pk

    -- Time-scoped send capability (plaintext, encrypted at rest at DB level)
    send_token          bytea NOT NULL,   -- 32 random bytes
    send_token_hash     bytea NOT NULL,   -- SHA-256 for lookup/deletion verification

    scheduled_at    timestamptz NOT NULL,
    status          text NOT NULL DEFAULT 'pending',  -- pending | sent | cancelled | expired
    created_at      timestamptz NOT NULL DEFAULT now(),
    sent_at         timestamptz,
    expires_at      timestamptz NOT NULL
);

-- send_token is encrypted at rest using the server's database encryption key
-- (see Server Secrets Architecture, Section 9)
```

### Lifecycle

```text
scheduled_at reached:
  1. BEGIN TRANSACTION
  2. SELECT send_token, encrypted_message, hpke_wrapped_key
     WHERE id = ? AND status = 'pending' AND scheduled_at <= now()
     FOR UPDATE
  3. Unwrap content_key using send_token + HPKE open
  4. Decrypt message body
  5. Send via outbound SMTP
  6. UPDATE status = 'sent', sent_at = now()
  7. DELETE send_token (SET NULL or overwrite with zeros)
  8. COMMIT

expires_at reached (cleanup job):
  1. UPDATE status = 'expired'
  2. DELETE send_token
  3. Optionally delete encrypted_message
```

### Security Properties

- send_token is usable exactly once (consumed on send)
- send_token expires (expires_at enforced by cleanup job)
- send_token is stored encrypted at rest at the database level
- send_token_hash enables deletion verification without holding plaintext longer than necessary
- The server can only decrypt this one message, only at the scheduled time, only with this token

## 3. Auto-Forward (REMOVED FROM V1)

### V5.0 Problem

Auto-forward requires the server to read the original message plaintext. The server does not have mailbox private keys. This makes auto-forward impossible under the stated crypto model without introducing a new server-side decryption exception.

### V5.1 Decision

**Auto-forwarding is removed from V1.**

Rationale:
- Auto-forward is the most dangerous automation feature: it operates continuously, copies plaintext to external recipients, and is difficult to audit.
- The architectural cost (new server-side decryption exception for an ongoing background process) is too high for V1.
- Users can forward manually through the webmail client.
- If auto-forward is needed later, it should be implemented as a client-side rule in the Bridge (V2), not a server-side process.

### V1 Alternative

Users who need forwarding can:
1. Use the webmail client to forward manually
2. Set up a client-side rule in their mail client (via Bridge, when available)

### Future Consideration

If server-side auto-forward is added post-V1, it must use an explicit scoped capability model similar to Scheduled Send:

```text
User authorizes forwarding rule
  ↓
Rule is stored as encrypted operational data
  ↓
When a new message arrives:
  - Server retrieves the forwarding rule
  - Server uses a scoped decryption capability (similar to send_token)
  - Server decrypts, forwards, destroys capability
  - Capability is single-message, per-rule
```

This is explicitly deferred to post-V1.

## 4. Auto-Reply (FIX)

### V5.0 Problem

The spec said "server decrypts auto-reply text using mailbox key for org-managed." The server does not have mailbox private keys. This is not possible.

### V5.1 Design

Auto-reply templates are explicitly stored as server-readable operational data. This is a conscious privacy tradeoff, not a crypto exception.

```text
User configures auto-reply
  ↓
Template stored as plaintext in database (server-readable)
  ↓
Server sends auto-reply when conditions match
  ↓
User is told: "Your auto-reply template is stored in readable form
              on our servers because automatic replies must operate
              while you're offline."
```

### Database Schema

```sql
CREATE TABLE auto_reply_rules (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    mailbox_id      uuid NOT NULL REFERENCES mailboxes(id),
    is_active       boolean NOT NULL DEFAULT true,

    -- Template stored as plaintext (server-readable)
    -- User consents to this during setup
    subject_template    text NOT NULL,
    body_template       text NOT NULL,

    -- Conditions
    reply_all           boolean NOT NULL DEFAULT false,
    allowed_senders     text[],          -- if set, only reply to these
    blocked_senders     text[],          -- if set, never reply to these
    start_time          timestamptz,
    end_time            timestamptz,

    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now()
);
```

### Privacy Disclosure

During auto-reply setup, the UI must display:

```text
Your auto-reply message will be stored in readable form on BYOS servers.
This is required because automatic replies must be sent even when you're
not online. BYOS staff can access this data. If this is not acceptable,
do not enable auto-reply.
```

### Future Consideration

Post-V1, a scoped capability model could allow encrypted auto-reply templates that are decrypted only when needed, similar to Scheduled Send.

## 5. Postfix Inbound Plaintext Handling (FIX)

### V5.0 Problem

The architecture claims "inbound plaintext exists for milliseconds and is never written to disk." But Postfix is a queueing MTA. Under failure conditions (storage unavailable, processing backlog), Postfix will persist plaintext messages to its queue directory on disk.

### V5.1 Design

Postfix handles SMTP receive and initial protocol processing only. The plaintext-to-encrypted transition must happen inside Postfix's content filter, before the message enters the Postfix queue.

```text
Internet email
  ↓
Postfix SMTP listener (port 25)
  ↓
Rspamd milter (spam check, header modification)
  ↓
Postfix content filter触发
  ↓
byos-inbound-bridge (Go service)
  ↓
Immediate encryption (within the content filter)
  ↓
Encrypted object written to customer storage
  ↓
Postfix queues the ENCRYPTED result (not plaintext)
  ↓
Delivery confirmation / bounce handling
```

### Architecture

```text
                  ┌─────────────────────┐
                  │   Postfix (smtpd)    │
                  │   port 25            │
                  └─────────┬───────────┘
                            │
                            ▼
                  ┌─────────────────────┐
                  │   Rspamd milter      │
                  │   (spam/DMARC check) │
                  └─────────┬───────────┘
                            │
                            ▼
                  ┌─────────────────────┐
                  │   byos-inbound-bridge│
                  │   (content filter)   │
                  │                      │
                  │  1. Parse MIME        │
                  │  2. Resolve mailbox   │
                  │  3. Fetch mailbox_pk  │
                  │  4. Generate content_key│
                  │  5. Encrypt message   │
                  │  6. Write to storage  │
                  │  7. Return OK + metadata│
                  └─────────┬───────────┘
                            │
                            ▼
                  ┌─────────────────────┐
                  │   Postfix (qmgr)     │
                  │   queues encrypted    │
                  │   result only         │
                  └─────────────────────┘
```

### The Inbound Bridge Service

`byos-inbound-bridge` is a Go service that acts as a Postfix content filter. It receives the full message from Postfix, encrypts it, and returns status.

```go
// byos-inbound-bridge/main.go
// Postfix content filter interface:
// Receives message on stdin, returns exit code:
//   0 = success (message stored encrypted)
//   100 = temporary failure (retry)
//   1 = permanent failure (bounce)

func main() {
    // Read message from stdin (Postfix pipes the message)
    msg, _ := io.ReadAll(os.Stdin)

    // 1. Parse MIME
    parsed, _ := mime.NewParser().Parse(msg)

    // 2. Resolve recipient mailbox
    mailbox, _ := resolveMailbox(parsed.To)

    // 3. Get mailbox public key
    mailboxPK, _ := getMailboxPublicKey(mailbox.ID)

    // 4. Generate content key
    contentKey := crypto.GenerateContentKey()

    // 5. Encrypt message
    encrypted := crypto.SealContent(contentKey, mailboxPK, msg)

    // 6. Write to customer storage
    storageID, _ := writeToStorage(mailbox, encrypted)

    // 7. Store metadata in database
    storeMetadata(mailbox, parsed, storageID, contentKey)

    // 8. Return success to Postfix
    os.Exit(0)
}
```

### Postfix Configuration

```.cf
# /etc/postfix/master.cf

# SMTP listener
smtp      inet  n       -       y       -       -       smtpd
  -o content_filter=byos:dummy

# Inbound bridge content filter
byos      unix  -       -       y       -       10      smtp
  -o smtp_send_xforward_command=yes
  -o smtp_discard_ehlo_keyword_address_maps=static:reject
```

### Failure Handling

```text
Customer storage unavailable:
  → byos-inbound-bridge returns temporary failure
  → Postfix queues the message (plaintext in queue)
  → This is the ONE exception to "no plaintext on disk"
  → Postfix queue is encrypted at rest (OS-level: LUKS/dm-crypt)
  → Retry until storage available or message expires

Postfix queue encryption:
  → Dedicated encrypted partition for Postfix spool
  → LUKS with server-managed key
  → Key in server secrets (Section 9)
  → This is explicitly documented as the ONLY plaintext persistence point
```

### Explicit Tradeoff

```text
"We guarantee no plaintext is written to customer storage or application
databases. During inbound processing, a brief plaintext existence occurs
in the Postfix queue under failure conditions. This queue is stored on an
encrypted partition (LUKS) managed by the server. This is the only
controlled exception to the zero-plaintext-persistence rule."
```

### V5.0 Problem

Tables were created in an order that violates foreign key constraints:
- `org_recovery_principals` references `users` before `users` exists
- `aliases` references `mailboxes` before `mailboxes` exists

## 7. HPKE Wire Format and Database Consolidation (FIX)

### V5.0 Problem

The wire format specified a single `hpke_wrapped` field but the database had multiple columns per cryptographic object (e.g., `encrypted_content_key`, `encrypted_content_key_enc`, `encrypted_content_key_ephemeral`, `encrypted_content_key_aad`).

### V5.1 Canonical Form

Every HPKE-wrapped value uses a single binary field in the database:

```text
hpke_wrapped = version(u8) || enc([u8;32]) || ciphertext([u8;N])
```

In the database: `bytea` column containing the canonical byte sequence.

Base64 encoding is for JSON/API transport only. The database stores raw bytes.

### Database Mapping

| Concept | V5.0 Columns | V5.1 Column |
|---------|-------------|-------------|
| Mailbox key wrapping | `encrypted_content_key`, `enc`, `ephemeral`, `aad` | `mailbox_sk_hpke_wrapped bytea` |
| Per-message content key | `encrypted_content_key`, `enc`, `ephemeral`, `aad` | `content_key_hpke_wrapped bytea` |
| Device root wrapping | `encrypted_root`, `enc`, `ephemeral`, `aad` | `root_hpke_wrapped bytea` |
| Org recovery root wrapping | `encrypted_root`, `enc`, `ephemeral`, `aad` | `org_recovery_root_hpke_wrapped bytea` |
| Scheduled send key | `encrypted_send_key`, `enc`, `ephemeral`, `aad` | `hpke_wrapped_key bytea` |

### Rust Type

```rust
/// Canonical HPKE wire format
pub struct HpkeWrapped {
    pub version: u8,           // 0x01
    pub enc: [u8; 32],         // DHKEM encapsulated key
    pub ciphertext: Vec<u8>,   // HPKE sealed ciphertext
}

impl HpkeWrapped {
    pub fn to_bytes(&self) -> Vec<u8> {
        let mut out = Vec::with_capacity(1 + 32 + self.ciphertext.len());
        out.push(self.version);
        out.extend_from_slice(&self.enc);
        out.extend_from_slice(&self.ciphertext);
        out
    }

    pub fn from_bytes(data: &[u8]) -> Result<Self, CryptoError> {
        if data.len() < 33 {
            return Err(CryptoError::InvalidFormat);
        }
        if data[0] != 0x01 {
            return Err(CryptoError::UnsupportedVersion);
        }
        let mut enc = [0u8; 32];
        enc.copy_from_slice(&data[1..33]);
        Ok(HpkeWrapped {
            version: data[0],
            enc,
            ciphertext: data[33..].to_vec(),
        })
    }
}
```

| Use | Info String |
|-----|-------------|
| Mailbox key wrapping | `"byos-mailbox-sk-v1"` |
| Content key sealing | `"byos-content-key-v1"` |
| Device root wrapping | `"byos-device-root-v1"` |
| Org recovery root wrapping | `"byos-org-recovery-v1"` |
| Scheduled send key | `"byos-send-token-v1"` |

## 8. DKIM Private-Key Management (NEW)

### V5.0 Gap

The domains table stored `dkim_public_key` but not the private signing key. Outbound DKIM signing requires the private key.

### V5.1 Design

```text
Domain verification
  ↓
Generate RSA 2048-bit key pair (or Ed25519)
  ↓
Private key stored encrypted in PostgreSQL (domains.dkim_private_key_enc)
  ↓
Public key published in DNS (DKIM record)
  ↓
Outbound signing layer reads private key at startup
  ↓
Signs outgoing messages
```

### Key Generation

```go
// During domain verification
func generateDKIMKeyPair() (publicKey string, privateKeyEnc []byte, err error) {
    // Generate RSA 2048-bit key
    priv, _ := rsa.GenerateKey(rand.Reader, 2048)

    // Serialize public key for DNS
    pubBytes, _ := x509.MarshalPKIXPublicKey(&priv.PublicKey)
    pubB64 := base64.StdEncoding.EncodeToString(pubBytes)

    // Encrypt private key with server key
    privBytes := x509.MarshalPKCS1PrivateKey(priv)
    privEnc, _ := serverEncrypt(privBytes)

    return pubB64, privEnc, nil
}
```

### DNS Record

```text
byos._domainkey.example.com.  IN  TXT  "v=DKIM1; k=rsa; p=MIIBIjANBg..."
```

### Signing Layer

```text
byos-outbound-bridge (Go service)
  ↓
On startup: load all active DKIM private keys from database
  ↓
Cache in memory (encrypted at rest in database, decrypted in memory only)
  ↓
For each outgoing message:
  1. Look up domain's DKIM private key
  2. Sign message body + selected headers
  3. Add DKIM-Signature header
  4. Pass to Postfix for delivery
```

### Security

- Private keys are encrypted in PostgreSQL with the server encryption key
- Private keys are loaded into memory only at startup
- Private keys are never written to disk unencrypted
- Key rotation: generate new key pair, update DNS, switch signing, revoke old key

### Bridge Protocol


## 11. Atomic Mailbox-Key-Version Selection During Rotation (FIX)

### V5.0 Gap

During key rotation, there was a race condition:

```text
T1: rotation starts
T2: inbound mail checks mailbox state
T3: rotation state changes
T4: inbound message chooses key version
T5: rotation commits
```

The inbound message could be encrypted with the wrong key version.

### V5.1 Design

The mailbox key state row must be locked atomically when selecting the key version for encryption.

```sql
-- Inbound message processing:
-- 1. Lock the mailbox row and read current key version
BEGIN;
SELECT mailbox_sk_version, mailbox_sk_hpke_wrapped
FROM mailboxes
WHERE id = $mailbox_id
FOR UPDATE;

-- 2. Use the locked version for encryption
-- 3. Insert message metadata referencing that version
INSERT INTO message_metadata (..., mailbox_sk_version)
VALUES (..., $selected_version);

COMMIT;
```

### Rotation Process

```sql
-- Rotation (also uses FOR UPDATE to prevent races):
BEGIN;

-- 1. Lock mailbox
SELECT mailbox_sk_version, mailbox_sk_hpke_wrapped
FROM mailboxes
WHERE id = $mailbox_id
FOR UPDATE;

-- 2. Generate new key
-- (new_sk = CSPRNG(32))

-- 3. Wrap new key with root
-- (hpke_wrapped_new = HPKE-Seal(new_sk, root_pk))

-- 4. Update version
UPDATE mailboxes
SET mailbox_sk_version = mailbox_sk_version + 1,
    mailbox_sk_hpke_wrapped = $hpke_wrapped_new,
    updated_at = now()
WHERE id = $mailbox_id;

-- 5. Messages after this point use new version

COMMIT;
```

### Property

At any point in time, exactly one key version is active for a mailbox. The FOR UPDATE lock ensures that inbound messages and rotation cannot interleave.

## 12. Unified Server-Side Automation Policy (NEW)

### V5.0 Gap

Each automation feature (search, scheduled send, auto-forward, auto-reply, subject filters) was designed separately with different privacy implications. No unified framework.

### V5.1 Automation Classification

Every server-side automation feature is classified into one of three categories:

### Category 1: Client-Only

Server never sees plaintext. All processing happens in the client (webmail or Bridge plugin).

```text
Features:
  → Search (encrypted search tokens, HMAC-based)
  → Contact management
  → Draft composition
  → Local filtering/rules
  → Mailbox organization (folders, labels)
```

Privacy guarantee: Server sees only opaque tokens and match counts.

### Category 2: Transient Server Plaintext

Server processes plaintext only when performing a necessary, bounded operation. Plaintext is never persisted.

```text
Features:
  → Inbound email processing (encrypt before storage)
  → Spam scanning (Rspamd sees plaintext briefly)
  → Content filter processing
  → Scheduled Send (server holds send_token, decrypts at scheduled time)
```

Privacy guarantee: Plaintext exists transiently in memory during the operation. No persistence.

### Category 3: Explicit Server-Readable Feature

User knowingly allows server access to specific data for automation. Clear consent during setup.

```text
Features:
  → Auto-reply (template stored as plaintext, user consents)
  → Subject-line display (for routing metadata, user consents during setup)
  → Recipient list (for delivery, necessary)
  → Sender address (for delivery, necessary)
```

Privacy guarantee: User is explicitly told what data is server-readable and why.

### Feature Classification Table

| Feature | Category | V1 Status | Notes |
|---------|----------|-----------|-------|
| Search | 1 - Client-only | Implemented | HMAC tokens, no plaintext |
| Scheduled Send | 2 - Transient | Implemented | send_token model |
| Auto-forward | Deferred | Removed V1 | Consider for V2 as Category 2 |
| Auto-reply | 3 - Server-readable | Implemented | Template stored plaintext |
| Subject display | 3 - Server-readable | Implemented | Metadata for routing |
| Recipient routing | 3 - Server-readable | Implemented | Necessary for delivery |
| Spam filtering | 2 - Transient | Implemented | Rspamd milter |
| Contact management | 1 - Client-only | Deferred | Client-side only |
| Draft sync | 1 - Client-only | Deferred | Client-side only |
| Folder/label rules | 1 - Client-only | Deferred | Client-side only |

### UI Requirement

When enabling a Category 3 feature, the UI must display:

```text
⚠️ Privacy Notice
This feature requires BYOS to store [specific data] in readable form.
This data will be accessible to BYOS staff. If this is not acceptable,
do not enable this feature.

[Enable Anyway] [Cancel]
```
