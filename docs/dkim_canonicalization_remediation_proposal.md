## Executive Summary & Approval Recommendation

External SMTP DKIM interoperability fails across **every outbound message signed by BYOS** (plain text, `multipart/alternative`, and Release B `multipart/mixed` / `multipart/related` attachment messages) when evaluated by independent RFC 6376 implementations. Cross-checking captured BYOS SMTP `DATA` bytes and eight freshly generated BYOS-signed message archetypes against both [`scratch/verify_dkim_rfc6376.mjs`](file:///f:/Codex/byos-email/scratch/verify_dkim_rfc6376.mjs) and an established third-party verifier (`mailauth` `8.0.6`) demonstrates that `byos_crypto_core::dkim_sign` and `byos_crypto_core::verify_dkim_signature` fail RFC 6376 (`c=relaxed/relaxed`) on **nine distinct defects** across both body canonicalization and header canonicalization / digest construction.

Existing BYOS self-tests inside [`packages/crypto-core/src/lib.rs#L2968-L3080`](file:///f:/Codex/byos-email/packages/crypto-core/src/lib.rs#L2968-L3080) and [`services/outbound-worker/src/main.rs#L7686-L7690`](file:///f:/Codex/byos-email/services/outbound-worker/src/main.rs#L7686-L7690) reported self-agreement only because `dkim_sign` and `verify_dkim_signature` invoke the **same non-RFC canonicalization helpers** (`relaxed_header_canonicalize` and `relaxed_body_canonicalize`), append the same non-standard trailing `\r\n` after `DKIM-Signature` in the RSA signing input, and assume `DKIM-Signature:` is header line `0`.

**Explicit Approval Recommendation:** Request formal engineering authorization to **narrowly unfreeze only the four DKIM functions in Section 12** of [`packages/crypto-core/src/lib.rs`](file:///f:/Codex/byos-email/packages/crypto-core/src/lib.rs) (`relaxed_header_canonicalize`, `relaxed_body_canonicalize`, `dkim_sign`, and `verify_dkim_signature`) plus targeted regression tests in `packages/crypto-core` and `services/outbound-worker`. Keep all HPKE (`RFC 9180`), X-Wing, AES-256-GCM envelope/attachment v2 formats, Ed25519 recovery, Postfix/DNS config, and database migrations strictly frozen and untouched.

## 3. Isolated Remediation Proposal

Because `packages/crypto-core/src/lib.rs` currently falls under Section 12 freeze rules, **no code changes were applied in this task**. The exact technical design below keeps the remediation strictly bounded to DKIM signing and verification inside [`packages/crypto-core/src/lib.rs`](file:///f:/Codex/byos-email/packages/crypto-core/src/lib.rs).

### 3.1 Proposed Header Parsing & `relaxed_header_canonicalize` (RFC 6376 §3.4.2)

1. **Unfold raw header section before parsing header fields** (`unfold_raw_headers(headers_str: &str) -> Vec<String>`):
   - Split header block on physical lines (`\r\n`, tolerating `\n` if internal callers supply LF).
   - Ignore empty lines; if a line begins with SP (`' '`) or HTAB (`'\t'`) and a previous header exists, append `\r\n` + line to that previous header verbatim (preserving raw bytes for future `simple` support while keeping full unfolded raw header).
   - Otherwise start a new header entry.

2. **Proposed `relaxed_header_canonicalize(raw_header: &str) -> String`:**
   - Split at the **first** `':'` (`(raw_name, raw_val)`). If none exists, trim ASCII WSP and lowercase ASCII.
   - Normalize `name`: `raw_name.trim_matches(|c| c == ' ' || c == '\t').to_ascii_lowercase()`.
   - Unfold continuation sequences inside `raw_val` per RFC 6376 §3.4.2 step 2: replace `"\r\n"` (or bare `"\n"` if already LF-normalized) when followed by WSP (`' '` / `'\t'`) or strip header-internal CRLFs before collapsing whitespace. Concretely, iterate bytes of `raw_val`: skip `\r` and `\n`, map every contiguous run of `' '` / `'\t'` (across any unfolded line break) to a single `' '`, and finally `.trim_matches(' ')` to remove all leading WSP after `:` and trailing WSP at end of line.
   - Emit `format!("{}:{}", canon_name, canon_val)` (single colon, zero space after colon, single spaces internally, no trailing CRLF).

### 3.2 Proposed `relaxed_body_canonicalize` (RFC 6376 §3.4.5)

Implement RFC 6376 §3.4.5 cleanly in byte space without doubling line endings or stripping `\r`:
```rust
fn relaxed_body_canonicalize(body: &[u8]) -> Vec<u8> {
    if body.is_empty() {
        return Vec::new();
    }
    // Split logical lines handling CRLF wires cleanly (and normalizing bare LF if present)
    let mut canon_lines: Vec<Vec<u8>> = Vec::new();
    let mut i = 0;
    while i <= body.len() {
        // Find next line ending (\r\n or \n)
        let line_start = i;
        while i < body.len() && body[i] != b'\n' && !(body[i] == b'\r' && body.get(i + 1) == Some(&b'\n')) {
            i += 1;
        }
        let line_slice = &body[line_start..i];
        // Advance past CRLF or LF; if at EOF with trailing empty slot after final newline, break
        let terminated = i < body.len();
        if i < body.len() {
            i += if body[i] == b'\r' { 2 } else { 1 };
        }
        if !terminated && line_slice.is_empty() {
            break;
        }

        // §3.4.5 step 1: trim trailing WSP, collapse internal [ \t]+ -> single 0x20
        let mut trimmed_end = line_slice.len();
        while trimmed_end > 0 && matches!(line_slice[trimmed_end - 1], b' ' | b'\t') {
            trimmed_end -= 1;
        }
        let mut line_out = Vec::with_capacity(trimmed_end);
        let mut in_wsp = false;
        for &b in &line_slice[..trimmed_end] {
            if b == b' ' || b == b'\t' {
                if !in_wsp {
                    line_out.push(b' ');
                    in_wsp = true;
                }
            } else {
                line_out.push(b);
                in_wsp = false;
            }
        }
        canon_lines.push(line_out);
        if !terminated {
            break;
        }
    }

    // §3.4.5 step 2: ignore all empty lines at the end of the message body
    while matches!(canon_lines.last(), Some(last) if last.is_empty()) {
        canon_lines.pop();
    }

    // Non-empty body: each line terminated by CRLF; empty body: 0 bytes
    let mut out = Vec::new();
    for line in canon_lines {
        out.extend_from_slice(&line);
        out.extend_from_slice(b"\r\n");
    }
    out
}
```
Behavior verification of the proposed algorithm on edge cases:
- `b""`, `b"\r\n"`, `b"\r\n\r\n"`, `b"   \t \r\n\r\n"` -> returns `b""` (SHA-256 `47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`).
- `b" C \r\nD \t E\r\n\r\n\r\n"` (RFC 6376 §3.4.5 example) -> returns `b" C\r\nD E\r\n"`.
- `b"Hello"` (no trailing CRLF) -> returns `b"Hello\r\n"`.
- Leading spaces (`b"  <p>Hello  world</p>\r\n"` in `case6`) -> collapses `"  "` to single `" "`, emitting `b" <p>Hello world</p>\r\n"`.

### 3.3 Proposed Changes to `dkim_sign` & `verify_dkim_signature`

1. **Shared Header Extraction & Selection:**
   - Replace `headers_str.lines()` in both `dkim_sign` (`L1430`) and `verify_dkim_signature` (`L1531`) with `unfold_raw_headers(headers_str)`.
   - Extract header `(raw_full_header, name_trimmed)` pairs rather than destructively splitting/rebuilding `"{}: {}"` (which alters spacing when `simple` canonicalization is later encountered or inspected).
   - **Signing order (`dkim_sign`):** Iterate raw headers bottom-to-top (per RFC 6376 §5.4 convention) or match the signed-header candidate set once per raw header index (`used` index tracking), emitting `h=` and `canonical_headers` in **exact 1:1 matching order**. Include `reply-to`, `sender`, `in-reply-to`, `references`, `content-disposition`, etc. as needed without breaking header uniqueness.
2. **RFC 6376 §3.7 Digest Construction:**
   - Append `relaxed_header_canonicalize(&dkim_header_without_b)` last.
   - Change signing digest input from `canonical_headers.join("\r\n") + "\r\n"` to **`canonical_headers.join("\r\n")`** (no trailing CRLF).
   - Optionally fold `DKIM-Signature:` at ~76 columns using `\r\n\t` continuation before prepending so `b=` stays comfortably under SMTP line limits (note: single-line `~500`-char `DKIM-Signature` is already below RFC 5322's 998-byte limit, and folding works seamlessly once `unfold_raw_headers` is active).
3. **RFC 6376 Verifier Alignment (`verify_dkim_signature`):**
   - Scan **all** unfolded headers to locate `DKIM-Signature:` (do not require line `0`).
   - Parse tags safely (`v=1`, `a=rsa-sha256`, `c=` validating header/body modes, `h=`, `bh=`, `b=`), stripping embedded whitespace/CRLF from `bh=` and `b=` before Base64 comparisons/decoding.
   - Strip `b=` value via tag-aware replacement (`b=` delimited by start/`;`/WSP, never colliding with `bh=` or base64 payload containing `b=`).
   - Select headers strictly from the parsed `h=` tag list using RFC 6376 §5.4 bottom-up occurrence matching (excluding `DKIM-Signature` itself), returning `false` if any `bh=` mismatch or RSA failure occurs.
   - Maintain the existing public function signature `pub fn verify_dkim_signature(signed: &[u8], public_key_pem: &str) -> bool` so all existing callers continue compiling unchanged.

### 3.4 Interaction with Outbound Pipeline (`strip_bcc_headers`, `assemble_mime_with_attachments`, `assemble_final_message`) & Ordinary Outbound Mail

Tracing [`services/outbound-worker/src/main.rs`](file:///f:/Codex/byos-email/services/outbound-worker/src/main.rs):
1. `strip_bcc_headers(&plaintext)` (`L277-L350`, called at `L2878` and again at `L3001` after attachment assembly) removes all `Bcc:` headers including folded continuation lines while preserving headers, delimiter, and body bytes verbatim. Because `dkim_sign` runs at `L3026` *after* both `assemble_mime_with_attachments` (`L2996`) and the second `strip_bcc_headers` (`L3001`), the MIME boundaries, `Content-Transfer-Encoding: base64` 76-char line wrapping, and 998-byte SMTP line lengths are already finalized before `bh=` is hashed. **Zero changes are required in `outbound-worker` assembly order.**
2. `assemble_final_message(&domain_name, &dkim_selector, &signed)` (`L420-L429`, called at `L3136`) prepends `Authentication-Results: ...` **above** `DKIM-Signature:` *after* signing. External verifiers (`Rspamd`, `mailauth`) locate `DKIM-Signature` regardless of prepended headers (`case7` check above). Once `verify_dkim_signature` searches all unfolded headers instead of `lines().next()`, `verify_dkim_signature(&final_message, &pub_pem)` will succeed directly on `assemble_final_message` output without requiring tests to strip `Authentication-Results:` ([`main.rs#L7686-L7689`](file:///f:/Codex/byos-email/services/outbound-worker/src/main.rs#L7686-L7689)).
3. **Impact on ordinary non-attachment outbound emails:** Ordinary plaintext (`case1`, `case8`) and `multipart/alternative` (`case6`) emails without attachments are **equally broken** by the current `relaxed_*_canonicalize`, `.lines()` unfolding omission, double colon, and trailing `\r\n` signing-input bugs. Remediating `packages/crypto-core` fixes external DKIM delivery across **all** outbound email paths simultaneously (plain, HTML, folded headers, `multipart/alternative`, `multipart/related`, and `multipart/mixed`).

## 6. Backward Compatibility & Legacy Signature Impact

- **Locally archived / stored user mailboxes (Path A / Sent / Archive):** Internal mailbox mail and drafts are end-to-end encrypted (`BYOS-SPEC-CRYPTO-ENV-V1` / Attachment v2) and do not rely on DKIM `Authentication-Results` signatures for decryption or integrity verification.
- **Previously delivered external outbound messages:** Messages already emitted to remote third-party MTAs carried the malformed BYOS signature (double colons + trailing CRLF + doubled-LF body canonicalization). Updating `dkim_sign` has no retroactive effect on already-delivered external mail.
- **Behavior of `verify_dkim_signature` on historical BYOS-signed samples:** Once `verify_dkim_signature` enforces RFC 6376 canonicalization, historical emails signed with pre-fix BYOS code will return `false`. Because `verify_dkim_signature` is not used in user-facing inbox display or production inbound verification flows (codebase search confirms calls exist only in [`packages/crypto-core/src/lib.rs#L3007-L3079`](file:///f:/Codex/byos-email/packages/crypto-core/src/lib.rs#L3007-L3079) and [`services/outbound-worker/src/main.rs#L7690`](file:///f:/Codex/byos-email/services/outbound-worker/src/main.rs#L7690)), and because external MTAs already rejected those signatures, maintaining legacy compatibility for broken double-colon signatures is **not recommended** — a single strict RFC 6376 parser avoids signature-malleability ambiguity.

## 7. Rollout Risks, Mitigations & Explicit Approval Checklist

### Rollout Risks & Mitigations

1. **Risk: Internal callers passing LF-only (`\n`) test strings into `dkim_sign`.**
   - *Mitigation:* Normalization of `\n` vs `\r\n` inside `dkim_sign` (already present at `lib.rs:1420-1425`) and CRLF canonicalization output ensures `bh=` matches wire SMTP (`\r\n`) while ensuring Postfix/SMTP transmission never converts LF differently from signing canonicalization (note `assemble_mime_with_attachments` and wire SMTP already use CRLF).
2. **Risk: Subtle difference between signed bytes and SMTP wire bytes (dot-stuffing or `Authentication-Results` insertion).**
   - *Mitigation:* Post-SMTP receiver strips dot-stuffing before `bh=` calculation per RFC 5321/6376, and `assemble_final_message` prepends `Authentication-Results` *outside* `h=`. Integration test using real mock SMTP DATA wire capture verifies post-dot-unstuffed `DATA` directly in `mailauth`.
3. **Risk: Tag-order or folded `b=` assumptions in downstream parser.**
   - *Mitigation:* Implement tag-boundary-safe `DKIM-Signature` parsing + bidirectional Rspamd/BYOS verification test (`rspamadm mime sign` -> `verify_dkim_signature`).
4. **Risk: Section 12 frozen boundary violation.**
   - *Mitigation:* Gate implementation strictly behind explicit written sign-off covering only the four DKIM functions in `packages/crypto-core/src/lib.rs` and associated unit/integration tests.
